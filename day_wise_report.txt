Day 1 Report — MiniDrive
========================

Overview
--------
This document summarizes the Day 1 work for the MiniDrive interview project: code added, the purpose of each function/module, why the chosen approach was used, trade-offs accepted, and realistic alternatives where relevant.

Files added (high level)
- minidrive/chunking.py — streaming chunk iterator and `Chunk` dataclass
- minidrive/distribution.py — `RoundRobinDistributor` (assign_by_index, assign_next)
- minidrive/replication.py — `Replicator` (replicate_chunk, _post_chunk_to_node)
- coordinator/main.py — FastAPI upload handler using streaming chunk writes
- storage-node/main.py — FastAPI endpoints to store and serve chunks
- frontend/* — Vite + React scaffold (package.json, index.html, src/App.jsx, src/main.jsx)
- tests/* — unit tests for chunking, distribution, replication
- README.md, requirements.txt

Day 1 Tasks (chronological)
----------------------------
1) Implement streaming chunking (minidrive/chunking.py)
   - What: `iter_chunks(stream, chunk_size)` yields `Chunk(index, data)` by repeatedly reading `chunk_size` bytes.
   - Why: Streaming keeps memory at O(chunk_size) rather than O(file_size). This is crucial for large uploads to avoid OOM and to enable immediate per-chunk processing (replication, hashing, metadata writes). Using the file object's .read(chunk_size) is the simplest, lowest-overhead way to stream a file without extra copies.
   - Trade-offs: Single-pass streaming prevents random access without reopening/rewinding the source. Also, callers must manage chunk indices if determinism is needed. We accepted this because uploads are typically streamed once and processed as they arrive.
   - Alternatives considered:
     * Read entire file then slice into chunks — simple to implement, but O(file_size) memory, unacceptable for large files.
     * Memory-mapped files — good for large local files but not available for streamed HTTP uploads.
   - Tests written: empty file, exact-boundary chunks, partial tail chunk, invalid chunk-size rejection.

2) Implement chunk distribution (minidrive/distribution.py)
   - What: `RoundRobinDistributor` with `assign_by_index(chunk_index)` and `assign_next()`.
   - Why: `assign_by_index` is stateless and deterministic (O(1) time, O(1) space). Determinism simplifies retries and idempotency: any worker can compute targets for a given chunk index independently.
   - Trade-offs: Round-robin by index ignores current node load and may cause uneven distribution if chunk sizes vary widely. `assign_next()` maintains mutable internal state and is protected by a small lock for thread-safety; used when callers don't want to track indices.
   - Alternatives considered:
     * Least-loaded selection (choose node with lowest current load): better balance in practice but requires tracking live metrics and synchronization (e.g., heap or sorted structure with O(log N) selection and updates), increasing complexity and race surfaces.
   - Tests written: assign_by_index mapping, assign_next sequence, empty-node list rejection.

3) Implement replication (minidrive/replication.py)
   - What: `Replicator.replicate_chunk(chunk)` attempts to write a chunk to `replication_factor` distinct nodes. It computes a deterministic candidate ordering starting at `chunk.index % N` and walks the ring trying nodes until the replication factor is met.
   - Why: Deterministic ordering allows independent orchestrators/clients to compute the same primary targets for a chunk and to retry in a predictable order. Sequential writes were chosen for simplicity and to reduce simultaneous network resource usage; error handling is straightforward (try next candidate on failure).
   - Trade-offs: Sequential writes increase wall-clock latency compared to parallel writes. We accepted sequential behavior for clarity and to keep resource usage low for an interview demo. Also, partial failures are handled by attempting alternate nodes; final failure raises a `ReplicationError` which the coordinator layer can handle (retry metadata, alert user, cleanup).
   - Alternatives considered:
     * Parallel writes to replication targets (fire off multiple requests concurrently) — reduces latency but requires aggregating results and handling partial-success semantics carefully (which nodes succeeded, which need cleanup or retry).
     * Background async replication with eventual consistency — more complex state tracking and reconciliation.
   - Tests written: full success, one node failing then alternate succeeds, all nodes failing raises `ReplicationError`.

4) Scaffolding: coordinator and storage-node FastAPI apps
   - What (coordinator/main.py): `POST /upload` endpoint accepts `UploadFile`, obtains its underlying `.file` binary stream, and writes chunk files (1MB default) using `iter_chunks`. Returns chunk count.
   - Why: Keeping the coordinator in Python/FastAPI keeps the file streaming code consistent and leverages FastAPI's straightforward async endpoints for later orchestration. FastAPI integrates well with uvicorn and asyncio if we later parallelize replication.
   - Trade-offs: Python is not as fast as some compiled servers, but for an interview prototype it reduces implementation complexity and testability. Node/Express was considered but provides no direct streaming advantage for this particular demo and would split the language surface.
   - What (storage-node/main.py): endpoints to `POST /chunks/{file_id}/{chunk_index}` (store raw bytes) and `GET /chunks/{file_id}/{chunk_index}` (stream the chunk back with a small read buffer).
   - Why: Keeping storage nodes minimalist (store/serve bytes) delegates control plane complexity to the coordinator and simplifies reasoning about node failure modes.
   - Trade-offs: Nodes currently accept raw bytes without checksums or partial-write detection. Day 2 should add integrity checks and conditional GET support (ETag/Last-Modified).

5) Frontend scaffold (frontend/)
   - What: Vite + React minimal scaffold with placeholder UI.
   - Why: React is ubiquitous for interview demos; Vite gives fast dev server and simple bundling. The frontend will later implement an upload component with progress reporting and a file browser.
   - Trade-offs: Minimal placeholder only; no production build configuration beyond Vite defaults.

Design notes and rationale (deeper detail)
-----------------------------------------
- Streaming vs read-then-split: streaming keeps memory bounded by the chunk size and begins useful work (replication/hashing) sooner. read-then-split needs the full payload resident in memory or in a temporary file, doubling I/O and using more disk or memory. For large files (100s of MB or GB) streaming is effectively required.

- Chunk size tradeoffs:
  * Too small (e.g., <=64KB): metadata explosion — more chunk records in DB, more network requests, and higher per-chunk overhead (HTTP headers, TCP handshake costs if not reused). Increases CPU overhead per chunk.
  * Too large (e.g., >=16MB): poor parallelism and coarser failure domains — a single slow node or network problem stalls more data; replication writes take longer and cause backpressure. Memory usage on nodes during transfer increases.
  * Middle ground (1MB): reasonable balance for demo/interview systems; supports parallelism and manageable metadata size.

- Distribution selection rationale:
  * Deterministic modulo mapping (`node = nodes[chunk_index % N]`) is O(1), stateless, and idempotent. Good for simple coordinator-less retries and predictable placement.
  * Real systems often combine consistent hashing (to scale node sets) or load-based selection. Consistent hashing reduces data movement under node membership changes but complicates replication target selection and requires more bookkeeping.

- Replication strategy rationale:
  * Chosen: write to `replication_factor` distinct nodes starting from a deterministic primary. Sequential attempts keep implementation simple and the error model predictable.
  * Alternatives: parallel writes (faster but more complex), quorum-based writes (used in distributed stores for strong guarantees), or erasure coding (space-efficient redundancy but complex encoding/decoding overhead).

Day 2 Report — MiniDrive
========================

Overview
--------
This document summarizes the Day 2 work for the MiniDrive interview project: the storage-node API, its content-addressed layout, and the reasoning behind the design choices.

Files added (high level)
- storage_node/main.py — FastAPI storage-node API using content-addressed chunk storage
- storage-node/main.py — legacy launcher for the storage node
- tests/test_storage_node.py — unit tests for store/get/delete and deduplication behavior
- requirements.txt — added runtime/test dependencies for FastAPI uploads
- README.md — documented the storage-node API and run commands

Day 2 Tasks (chronological)
---------------------------
1) Build the storage-node API (storage_node/main.py)
   - What: Implemented `POST /chunks`, `GET /chunks/{hash}`, and `DELETE /chunks/{hash}` for chunk storage.
   - Why: The storage node should only store and serve raw chunk bytes. Keeping the API small makes failure modes easier to reason about and keeps the coordinator in charge of control-plane logic.
   - Trade-offs: The node currently does not track chunk reference counts or garbage collection across files that may share the same content hash.
   - Alternatives considered:
     * Sequential IDs with a separate metadata index — easier to read manually, but it does not naturally support deduplication.
     * UUID-based names — unique, but still not content-aware, so integrity verification and dedupe remain separate concerns.

2) Use content-addressed storage with hash-prefix sharding
   - What: Stored each chunk under a path derived from its SHA-256 hash, using the first two hex characters as a directory prefix and the remainder as the filename.
   - Why: Content-addressed storage provides deduplication because identical bytes map to the same hash. It also provides integrity verification because the hash is derived from the data itself. Hash-prefix sharding keeps directory sizes manageable and avoids putting too many files in one folder.
   - Trade-offs: Hash-based paths are longer and less human-friendly than sequential IDs, and delete operations may need later garbage collection if the same chunk is referenced by multiple files.
   - Alternatives considered:
     * Flat directory by hash — simpler, but large directories can become slow to list and manage.
     * Sequential IDs — simple naming, but no built-in dedupe or integrity guarantee.

3) Stream chunk writes through a temporary file before commit
   - What: Read the request body as a stream, update a SHA-256 digest incrementally, and write bytes to a temporary file before atomically moving it into place.
   - Why: Streaming keeps memory usage bounded by the chunk size instead of the full request size. The temp-file-and-rename pattern avoids partially written final objects if the request is interrupted or the hash check fails.
   - Trade-offs: This is slightly more disk-heavy than writing directly to the final path, but the safety and atomicity are worth it for a storage node.
   - Alternatives considered:
     * Buffer everything in memory first — simple, but memory usage grows with file size.
     * Write directly to the final file — faster in the happy path, but risks leaving corrupted partial objects.

4) Add tests for round-trip storage, deduplication, and hash mismatch rejection
   - What: Added unit tests that upload a chunk, retrieve it, delete it, upload it twice to check deduplication, and reject mismatched hashes.
   - Why: These tests prove the API works for the core storage lifecycle and catch the main correctness risks: duplicate writes, corrupted uploads, and missing cleanup.
   - Trade-offs: The tests exercise the public API, not filesystem edge cases like permission errors or disk exhaustion.
   - Alternatives considered:
     * Mocking every filesystem call — more isolated, but less representative of the real behavior.
     * End-to-end tests against a running server — useful later, but slower than unit tests for this stage.

5) Update project documentation
   - What: Updated `README.md` with the repo layout, run commands, and the storage-node curl examples.
   - Why: The README now reflects the actual workspace structure and gives a fast path for reviewers to run the Day 2 API.
   - Trade-offs: The README is intentionally concise, so deeper architecture details remain in this report.

Testing and validation
----------------------
- Ran the full Python unit test suite after the storage-node API changes.
- Result: all tests passed.

Design notes and rationale
--------------------------
- Content-addressed storage was preferred over sequential IDs because it makes deduplication and integrity verification properties of the naming scheme itself.
- The hash-prefix directory layout is a practical compromise between simplicity and filesystem scalability.
- Streaming the upload body through a digest and temporary file keeps memory usage low while preserving atomic commit semantics.

End of Day 2 report.

Day 3 Report — MiniDrive
========================

Overview
--------
This document summarizes the Day 3 integration work for MiniDrive: wiring the existing chunking, distribution, replication, and storage-node modules into one end-to-end upload flow, then proving the flow with a real multi-chunk file.

Files updated (high level)
- coordinator/main.py — upload endpoint now computes chunk hashes, assigns targets, replicates over HTTP, and returns per-chunk results
- minidrive/replication.py — POSTs chunks to storage nodes with the required `X-Chunk-Hash` header
- minidrive/config.py — static storage-node URL list and replication factor
- tests/test_upload_integration.py — integration test for the coordinator upload path against in-process storage nodes

Day 3 Tasks (chronological)
---------------------------
1) Wire the coordinator upload path end to end (coordinator/main.py)
  - What: Updated `POST /upload` to stream chunks from `iter_chunks`, compute each chunk's SHA-256 hash, determine the primary node with `RoundRobinDistributor.assign_by_index()`, call `Replicator.replicate_chunk()`, and collect a structured per-chunk result.
  - Why: The coordinator now acts as the control plane for the upload flow instead of only chunking locally. That lets it produce the chunk metadata a future database layer will need without adding new distributed-system features yet.
  - Trade-offs: The endpoint still uses a simple in-memory response structure rather than persisting metadata. That is intentional for this integration milestone: it proves the transport and placement logic first, before adding atomic database writes or recovery logic.
  - Function-by-function:
    * `upload()` streams the file, computes hashes, triggers replication, and returns `file_id`, `total_chunks`, and per-chunk status.
    * `_replica_targets_for_chunk()` derives the target node set from the round-robin placement so the response can show which nodes were intended for each chunk.

2) Align replication with the storage-node API (minidrive/replication.py)
  - What: Changed `_post_chunk_to_node()` to send the chunk bytes to `/chunks` with an `X-Chunk-Hash` header, matching the storage-node contract.
  - Why: The storage node is content-addressed and verifies the payload hash before committing the object. Without the header, the coordinator could not store data successfully.
  - Trade-offs: Replication is still sequential, which keeps the error handling simple and deterministic but is slower than parallel writes. That was acceptable for proving correctness first.
  - Function-by-function:
    * `replicate_chunk()` still chooses candidates deterministically and retries on alternate nodes until the replication factor is met.
    * `_post_chunk_to_node()` now constructs the correct HTTP request for the storage-node API.

3) Add static node configuration (minidrive/config.py)
  - What: Added a hardcoded list of 2-3 storage-node URLs and a replication factor constant.
  - Why: Discovery was intentionally deferred. Hardcoding the node list makes the integration path easy to reason about and test while we validate the rest of the stack.
  - Trade-offs: This does not scale to a dynamic cluster. That is fine for now because the goal was to prove the upload flow works before introducing another moving part.

4) Prove the flow with an integration test (tests/test_upload_integration.py)
  - What: Added an integration test that spins up isolated in-process storage-node apps, uploads a multi-chunk file through the coordinator's `/upload` endpoint, and verifies each returned hash by querying `GET /chunks/{hash}` directly.
  - Why: This tests the real handoff between coordinator and storage nodes instead of only mocking helper functions. It catches mismatches in request format, headers, chunk hashing, and chunk placement.
  - Trade-offs: The test uses in-process FastAPI apps instead of separate OS processes, so it validates the HTTP contract and storage behavior but not process supervision or network bootstrapping.

Testing and validation
----------------------
- Ran the new integration test: passed.
- Ran the full Python unit test suite: passed.
- Manually uploaded a 5MB+ file through the coordinator and verified the stored chunk files on disk under each storage node's hash-prefixed directories.

Debugging log
-------------
- Bug 1: The replication layer was posting raw bytes without the `X-Chunk-Hash` header required by the storage-node API. This showed up as a contract mismatch once I traced the coordinator path into storage-node `POST /chunks`. Fix: compute the chunk hash in `_post_chunk_to_node()` and include it in the request headers.
- Bug 2: The coordinator still only chunked locally and returned a count, so the storage nodes were never reached. This was visible from the existing `coordinator/main.py` flow, which had no call into `Replicator`. Fix: replaced the local file-write loop with replication calls and a structured per-chunk result.
- Bug 3: The integration test needed isolated node state so that one node's stored chunks would not bleed into another test run. Fix: load the storage-node app into separate module instances and override each module's `STORAGE_DIR` with a temporary directory before creating the test client.

Replicator and distributor outcome
----------------------------------
- `RoundRobinDistributor.assign_by_index()` worked as designed once it was used against real node URLs. No algorithmic changes were needed.
- `Replicator.replicate_chunk()` also worked as designed for sequential replication. The only change required was aligning the HTTP request shape with the storage-node API.
- In other words, the integration work did not require a new placement algorithm or a different replication strategy; it required wiring the existing pieces together with the correct transport contract.

End of Day 3 report.
